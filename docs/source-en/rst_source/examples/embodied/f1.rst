RL with F1 Dual-Arm Peg Insertion
=================================

Train a CNN policy for F1 dual-arm peg insertion with online SAC or RLPD. The
GPU node runs Actor and Rollout workers, while the robot-side node runs the Env
Worker and the ROS 2 Controller backend.

Overview
--------

Configure the robot and training settings in one Hydra YAML, diagnose the
Controller, launch the two-node Ray cluster, and start training from the GPU
head node.

Observation and Action
~~~~~~~~~~~~~~~~~~~~~~

.. list-table::
   :header-rows: 1
   :widths: 25 27 24 24

   * - Observation
     - Action
     - Reward
     - Prompt
   * - Three RGB streams: ``head_color``, ``left_wrist_color``, ``right_wrist_color``; 16D arm/gripper state
     - 14D normalized action in ``[-1, 1]``. The Env maps it to left/right TCP deltas and gripper targets.
     - Task reward and success signal returned by ``F1DualArmPegInsertionEnv-v1``. Controller faults stop motion and reject the step.
     - ``Use both arms cooperatively to insert the peg into the matching hole.``

Right-Arm Fixed-Target Variant
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Use ``realworld_f1_right_arm_peg_rlpd_cnn_async`` for the simplified task in
which the right gripper already holds the insert and the hole is fixed. Its
``F1RightArmPegInsertionEnv-v0`` policy interface contains one
``head_color`` image, a 6D right TCP pose, and a 6D normalized right TCP delta.
The wrapper sends zero deltas to the left arm and both grippers, so they hold
their measured state.

The only task calibration is ``target_tcp_pose_m_deg``, a final
``[x, y, z, rx, ry, rz]`` pose in meters and degrees read from
``/state/right_arm/tcp_pos``. Its reference is the controller-native
``right_arm_tcp_pose`` frame. No pre-insert waypoint or approach axis is
required, so demonstrations may approach the target from different paths.

The dense reward is the change in a weighted, normalized linear
position-and-orientation target potential, minus ``step_penalty``. Unlike an
exponential potential, it still provides a gradient when the TCP starts far
from the target. Holding still away from success cannot accumulate positive
reward. Success requires both errors to remain
within their tolerances for ``success_hold_steps``, adds one bonus, and ends the
episode because ``ignore_terminations`` is false. The horizon is 50 policy
steps (5 seconds at 10 Hz). The task configuration first runs
``algorithm.bc_warmup_updates`` demo-only Gaussian behavior-cloning updates on
the same CNN actor, saves ``global_step_0``, and then starts asynchronous RLPD.
``algorithm.update_epoch`` controls the SAC replay updates per online step.
Set ``algorithm.bc_log_interval`` to control how often ``bc/loss`` and
``bc/action_mae`` points are written to TensorBoard during warmup.
Regenerate the demonstration buffer whenever the shared reward definition
changes so offline and online transitions use identical rewards.

Right-Arm XYZ Reach Curriculum
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Use ``realworld_f1_right_arm_reach_sac_cnn_async`` to train the first
curriculum stage without demonstrations. ``F1RightArmFixedReachEnv-v0``
observes the complete right-wrist RGB frame resized directly from
``848×480`` to ``224×128`` and the measured right TCP XYZ position. The policy
outputs three normalized XYZ deltas; the environment holds TCP orientation at
``[90, 0, 90]`` degrees and leaves the other actuators unchanged.

The checked-in configuration applies a 5 mm action scale and clips every
candidate TCP position inside the calibrated target-relative box in the
``base_link`` coordinate convention. It trains SAC from online replay only:
``algorithm.demo_buffer`` is null and ``algorithm.bc_warmup_updates`` is zero.
Before running on hardware, verify the target pose, reset joint poses,
``vendor_to_base_rotation``, and workspace offsets for the current robot setup.

Architecture and Node Roles
---------------------------

Run the entry script only on the GPU head node. The head trains the Actor and
runs Rollout inference. The robot-side worker hosts the Env Worker and
Controller backend. The current container is validated on NVIDIA Thor, but the
runtime boundary is an ARM64 Linux node with ROS 2 Jazzy.

.. list-table::
   :header-rows: 1
   :widths: 20 26 54

   * - Node
     - Rank
     - Role
   * - GPU server
     - ``RLINF_NODE_RANK=0``
     - Ray head, ActorGroup, RolloutGroup, replay sampling, optimizer, and logs.
   * - F1 robot node
     - ``RLINF_NODE_RANK=1``
     - Ray worker, EnvGroup, Controller ``backend: ros2``, sensor reads, and bounded commands.

.. warning::

   Set ``RLINF_NODE_RANK`` before ``ray start`` on each node. Ray captures the
   environment at startup, so changing the variable later does not repair node
   placement.

Installation
------------

Prepare the GPU Python environment and robot-side image with the runtime guide:
:doc:`F1 Two-Node Runtime </rst_source/guides/f1_runtime>`.

On the GPU server, install the embodied dependencies and then apply the shared
F1 runtime constraints and Controller package to the same Python ``3.12.3``
environment:

.. code-block:: bash

   bash requirements/install.sh embodied \
     --env dummy \
     --python 3.12.3 \
     --venv .venv-f1 \
     --install-rlinf
   F1_ROBOT_CONTROLLER_PACKAGE=<wheel-path-package-url-or-pinned-git-url> \
     bash requirements/install.sh f1-realworld \
       --python 3.12.3 \
       --venv .venv-f1
   source .venv-f1/bin/activate
   python -c "import f1_robot_controller, platform, ray; assert platform.python_version() == '3.12.3'; assert ray.__version__ == '2.57.0'; assert callable(f1_robot_controller.create_controller)"

On the robot computer, use the F1 container image built from
``docker/f1/Dockerfile``. It contains ROS 2 Jazzy, the supplied Controller
package, Ray ``2.57.0``, and the RLinf source.

What this does: the GPU env keeps CUDA/training dependencies on the server; the
robot-side image keeps ROS 2 and robot communication on the robot computer.

Download the Model
------------------

Download the pretrained ResNet CNN backbone on the GPU server:

.. code-block:: bash

   hf download RLinf/RLinf-ResNet10-pretrained \
     --local-dir RLinf-ResNet10-pretrained

Set ``actor.model.model_path`` to the downloaded directory. Rollout uses the
same path through ``${actor.model.model_path}``.

Edit One YAML
-------------

Start from ``examples/embodiment/config/realworld_f1_peg_rlpd_cnn_async.yaml``.
Keep the runtime contract inline:

.. code-block:: yaml

   runner:
     logger:
       log_path: ./logs/f1-peg-rlpd
   actor:
     model:
       model_path: /path/to/RLinf-ResNet10-pretrained
   rollout:
     model:
       model_path: ${actor.model.model_path}
   env:
     train:
       max_episode_steps: 10
       max_steps_per_rollout_epoch: 10
       override_cfg:
         controller:
           backend: ros2
         action_scale:
           tcp_position_m: 0.005
           tcp_orientation_deg: 1.0
           gripper_percent_closed: 10.0
         motion_envelope:
           gripper_percent_closed: [0.0, 100.0]
         max_num_steps: 10

What this does: ``controller.backend`` selects ``fake`` or ``ros2``;
``action_scale`` maps policy actions to meters, degrees, and gripper percent;
``motion_envelope`` is the Controller safety boundary. Override ordinary keys
with Hydra CLI syntax, for example ``actor.model.model_path=/models/f1-cnn`` or
``runner.logger.log_path=/runs/f1-train``.

Run Controller Diagnostics
--------------------------

Run diagnostics on the robot-side node before any RLinf entry script starts:

.. code-block:: bash

   controller_json="$(mktemp /tmp/f1-controller.XXXXXX.json)"
   EMBODIED_PATH="$PWD/examples/embodiment" \
   python - "$controller_json" <<'PY'
   import json
   import sys
   from pathlib import Path

   from hydra import compose, initialize_config_dir
   from omegaconf import OmegaConf

   output = Path(sys.argv[1])
   with initialize_config_dir(
       config_dir=str(
           Path.cwd() / "examples" / "embodiment" / "config"
       ),
       version_base=None,
   ):
       cfg = compose(config_name="realworld_f1_peg_rlpd_cnn_async")
   override_cfg = OmegaConf.to_container(
       cfg.env.train.override_cfg,
       resolve=True,
   )
   controller = dict(override_cfg["controller"])
   controller["motion_envelope"] = override_cfg["motion_envelope"]
   output.write_text(json.dumps(controller, indent=2, sort_keys=True) + "\n")
   PY
   f1-controller doctor --config "$controller_json"
   f1-controller read-state --config "$controller_json"

What this does: you keep editing one Hydra YAML, then extract the
Controller-owned mapping plus sibling ``motion_envelope`` into a temporary
controller JSON for the CLI. ``f1-controller doctor`` checks ROS 2 discovery,
topic types, freshness, skew, and read-only connectivity. ``f1-controller
read-state`` prints the normalized current robot state.

Start Ray on Both Nodes
-----------------------

Start Ray after sourcing the setup script on both nodes.

On the GPU server:

.. code-block:: bash

   export F1_RUNTIME_ROLE=gpu
   export F1_VENV_PATH="$PWD/.venv-f1"
   export RLINF_COMM_NET_DEVICES=<GPU_INTERFACE>
   export RLINF_NODE_RANK=0
   source ray_utils/realworld/f1/setup_before_ray.sh
   ray start --head --port=6379 --node-ip-address=<GPU_SERVER_IP>

On the robot-side ARM64 node (validated on NVIDIA Thor):

.. code-block:: bash

   docker run --rm --network host --name f1-ray-worker f1-rlinf-env:runtime-simplified bash -lc '
     export F1_RUNTIME_ROLE=thor
     export F1_VENV_PATH=/opt/rlinf-venv
     export RLINF_COMM_NET_DEVICES=<THOR_INTERFACE>
     export RLINF_NODE_RANK=1
     source ray_utils/realworld/f1/setup_before_ray.sh
     ray start --address=<GPU_SERVER_IP>:6379 --node-ip-address=<THOR_IP> --block
   '

Prepare Demonstrations for RLPD
-------------------------------

The F1 RLPD configuration requires a non-empty demonstration buffer. Set
``algorithm.demo_buffer.load_path`` to an RLinf replay buffer collected for the
same task, with the same observation and 14-dimensional action shapes.

To train with online SAC only, remove the demo-buffer mapping:

.. code-block:: bash

   '~algorithm.demo_buffer'

Run It
------

Confirm that the workcell is clear, the emergency stop is reachable, and a
trained operator is supervising the robot. Then launch RLPD training from the
GPU head:

.. code-block:: bash

   EMBODIED_PATH="$PWD/examples/embodiment" \
   python examples/embodiment/train_async.py \
     --config-name realworld_f1_peg_rlpd_cnn_async \
     actor.model.model_path=/path/to/RLinf-ResNet10-pretrained \
     algorithm.demo_buffer.load_path=/path/to/f1-peg-demo-buffer

For online SAC without demonstrations, append:

.. code-block:: bash

   '~algorithm.demo_buffer'

What this does: ActorGroup and RolloutGroup run on the ``gpu`` node group;
EnvGroup runs on the ``f1`` node group through ``/opt/rlinf-venv/bin/python``.
Set ``env.train.max_episode_steps``,
``env.train.max_steps_per_rollout_epoch``, and
``env.train.override_cfg.max_num_steps`` to control the collection horizon.

Visualization and Results
-------------------------

Inspect logs and replay before repeating a real run.

.. list-table::
   :header-rows: 1
   :widths: 34 66

   * - Output
     - Check
   * - ``./logs/f1-peg-rlpd``
     - Open TensorBoard and inspect SAC losses, replay counts, and timing. See :doc:`Training Metrics </rst_source/reference/metrics>`.
   * - ``./logs/f1-peg-rlpd/online-replay``
     - Confirm that the online replay buffer is written and its sample count grows with collection.
   * - Safety stop
     - Stop the runner with ``Ctrl+C``, then run ``ray stop`` on both nodes. If a Controller fault appears, stop robot motion first and discard the incomplete trajectory.
